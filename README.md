# Bookstore Manager

One codebase, two ways to run it:

- **Web** — `web/` is deployed to Vercel. Installable from Chrome or Edge ("Install app").
- **Windows** — `src-tauri/` wraps the *same* `web/` folder into an `.exe`, and updates itself from GitHub Releases.

Change something in `web/index.html` and both get it: the web app on the next deploy, the desktop app the next time it starts.

```
web/                  the app — this is the whole frontend
  index.html            single-file app (UI + logic + offline layer)
  sw.js                 service worker: caches the shell so it opens offline
  manifest.webmanifest  makes it installable
  vendor/supabase.js    bundled, not from a CDN — the app must start with no internet
  icons/
src-tauri/            the Windows desktop shell
.github/workflows/    builds and publishes the installer on a version tag
supabase-schema.sql   the database
```

---

## 1. Database

Run `supabase-schema.sql` once in the Supabase SQL editor.

It **drops and recreates** the tables. The keys are now `uuid` instead of `bigserial`, because a till that is offline has to create rows without asking the server for a number.

Two other things changed for offline:

- `receipt_no` is text and is generated by the app (highest existing number + 1), not by the database. It is unique per user, so a replayed queue can never overwrite an earlier receipt.
- Every table has `updated_at`, stamped by a trigger.

---

## 2. How offline works

The app never talks to Supabase to answer a question. It reads from an in-memory copy that is mirrored into **IndexedDB**, so everything renders instantly and works with the network unplugged.

Every write does three things, in this order:

1. updates the in-memory copy, so the screen reacts immediately
2. saves the whole snapshot to IndexedDB, so it survives closing the app
3. appends the change to an **outbox** queue

The sync engine drains that queue whenever a connection exists — on launch, when Windows reports the network is back, every 60 seconds, and when you press **Sync now** in Settings. It always pushes the queue *before* pulling fresh data down, so nothing you did offline can be overwritten by the pull.

The pill in the header tells you where you stand: `Synced`, `3 waiting to sync`, `Offline · 3 waiting`, `Syncing…`.

**Signing in needs a connection the first time on each device.** After that the session is remembered and the app opens straight into the till with no internet.

**Signing out wipes the local copy.** If the outbox is not empty it warns you first and names how many changes would be lost.

### The one rule

Only one device may work offline at a time. Conflicts are resolved last-writer-wins, and stock is a plain number, so if a second till sold the same books while this one was offline, whichever syncs last wins for that book. With a single till this cannot happen.

## 3. Web deployment (Vercel)

Nothing to configure — `vercel.json` sets the site root to `web/`. Push to `main` and Vercel serves the new version. `/bookstore.html` redirects to `/` so old bookmarks keep working.

Every deploy should bump `CACHE` in `web/sw.js` (for example `bookstore-shell-v2`) so installed copies pick up the change instead of serving the old shell.

## 4. Windows app

### One-time setup

You need [Node](https://nodejs.org), [Rust](https://rustup.rs) and the Visual Studio C++ build tools. Then:

```bash
npm install
```

**Generate the update signing key** — this is what proves an update really came from you:

```bash
npm run keygen
```

It prints a public key and writes a private key. Then:

1. Paste the **public** key into `src-tauri/tauri.conf.json` → `plugins.updater.pubkey`.
2. In GitHub → Settings → Secrets and variables → Actions, add:
   - `TAURI_SIGNING_PRIVATE_KEY` — the contents of the private key file
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — the password you chose (add it even if empty)
3. In GitHub → Settings → Actions → Workflow permissions, pick **Read and write permissions**.

Keep the private key somewhere safe. Losing it means installed copies can no longer verify updates and everyone has to reinstall by hand.

### Build locally

```bash
npm run dev      # opens the app with live reload
npm run build    # produces the installer
```

The installer lands in `src-tauri/target/release/bundle/nsis/`.

### Release an update

```bash
# bump the version in BOTH src-tauri/tauri.conf.json and src-tauri/Cargo.toml
git commit -am "v1.0.1"
git tag v1.0.1
git push BookStore main --tags
```

GitHub Actions builds the installer, signs it, and publishes it together with `latest.json`. Installed copies check that file on every launch, and install a newer version silently with a progress bar. With no connection the check fails quietly and the app opens as usual.

The version in `tauri.conf.json` is the one the updater compares, so it must go up every release.

## 5. Notes

- The Supabase publishable key in `index.html` is meant to be public. Row Level Security is what protects the data — every policy restricts rows to `auth.uid()`.
- The desktop build runs no content security policy on purpose: Tauri injects nonces when a CSP is set, which would disable the inline `onclick` handlers the app uses. Nothing remote is loaded, so there is no remote code to restrict.
- The service worker is skipped inside the desktop app, which already runs from local files.
- `Export Backup (JSON)` still works and is worth doing occasionally — it is a copy that does not depend on Supabase or on this machine.
